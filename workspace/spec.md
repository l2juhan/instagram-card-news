## 슬라이드 설계

### 슬라이드 1: cover
- 목적: "이 컴포넌트, 결국 무슨 일을 하는 거지?"라는 통증 자극 훅
- 핵심 메시지: 구현 상세를 그대로 드러내면 읽기 어렵다 → 추상화로 맥락을 줄이자
- 목표 감정: "내 컴포넌트도 다 드러나 있는데" 자기인식 + 호기심
- 라벨 "가독성", 우측 하단 출처(Toss Frontend Fundamentals), 부제목 없음

### 슬라이드 2: content-highlight
- 목적: 원칙 한 줄로 못박기 (읽는 사람의 맥락은 한정 → 추상화로 제한)
- 핵심 데이터: 원문 인용 — "동시에 고려할 수 있는 맥락의 숫자는 제한되어 있다"
- 콘텐츠 밀도: 중간

### 슬라이드 3: content (Before 코드)
- 목적: 구현 상세가 노출된 문제 코드를 실물로 제시. 좌측 경계 빨강(문제 신호)
- 핵심 데이터: 원문 Before LoginStartPage (useCheckLogin/onChecked/status 분기 노출)
- 콘텐츠 밀도: 높음 (코드 블럭)

### 슬라이드 4: content
- 목적: 무엇이 문제인지 언어로 해부 (세부사항 동시 이해 부담 + 인증/화면 로직 혼재)
- 핵심 데이터: 인지 부담 = 동시에 추적할 맥락 증가
- 콘텐츠 밀도: 중간

### 슬라이드 5: content (After 코드)
- 목적: 개선 코드 실물. 좌측 경계 그린(해결 신호)
- 핵심 데이터: 원문 After 옵션 A — App이 AuthGuard로 감싸고, 인증 분기는 AuthGuard가 책임
- 콘텐츠 밀도: 높음 (코드 블럭)

### 슬라이드 6: content-split
- 목적: Before/After 본질 차이를 한 화면에 대조
- 핵심 데이터: 상세 노출·역할 모호 vs 단일 관심사·역할 또렷
- 콘텐츠 밀도: 중간

### 슬라이드 7: content-list
- 목적: 실전 적용 신호 체크리스트 (언제 추상화하나)
- 핵심 데이터: 추상화 신호 5가지
- 콘텐츠 밀도: 중간

## 디자인 노트
- 색상: toss 블루(#3182F6)를 원칙/해결의 긍정 신호로, Before 코드에는 빨강(#FF5C5C) 좌측 경계로 문제 신호 대비, After 코드에는 그린(#3DDC97)
- 시각적 리듬: 원칙(가벼움) → Before 코드(밀도↑) → 해부(가벼움) → After 코드(밀도↑) → 대조 → 정리
- toss 특화: 다크 플랫(#191F28) + JetBrains Mono 코드블럭, One Dark Pro 신택스(키워드 #C678DD, 문자열 #98C379, 함수 #61AFEF, JSX 태그 #E5C07B, 주석 #5C6370)
- toss는 1080×1350(세로) → 콘텐츠 적은 슬라이드는 수직 중앙 정렬 + 폰트 확대로 빈 공간 50% 규칙 준수
- style_override는 content를 코드블럭으로 변형/여백 보정에만 사용 (브랜드 골격 유지)

## 리서치 요약
한 번에 고려할 맥락이 한정된 상태에서 구현 상세를 그대로 드러내면 컴포넌트 역할이 흐려진다. LoginStartPage의 로그인 체크 분기를 AuthGuard 래퍼로 추상화하면 부모는 감싸기만 하고 화면 컴포넌트는 화면에만 집중하므로, 읽는 사람이 한 번에 볼 맥락이 줄어든다.
